# Analytics opt-out and erasure — design and inventory, not implemented

The owner chose deletion of identifiable server analytics on tracking opt-out and account deletion, retaining only genuinely non-identifying totals if needed. This decision does **not** authorize deleting existing live data, changing backups, or accessing personal content. No deletion has been performed. Opt-out must stop future collection/use and delete already collected identifiable analytics across the approved scope; a local-only switch is not sufficient.

## Code inventory (local repository, not an assertion of live configuration)

| Surface | What the code does | Gap |
|---|---|---|
| Browser IndexedDB and query cache | `lib/local-analytics-control.ts` holds a browser-wide preference/epoch, gates local recording and visibility, and settings can clear local events. `lib/analytics.ts` bounds its local events and clears queued work on a control change. | Not account-wide; other devices/browser profiles, in-flight requests already received and previously uploaded server events are not covered. Storage failures, browser shutdown and old clients need handling. |
| Browser session storage and in-memory queue | Session IDs and queued event records exist in the browser; queue is cleared and active request aborted on local change. | Aborting a request does not undo server processing; local session identity alone cannot authorize an account erasure. |
| API `POST /api/events` | Accepts unauthenticated client event IDs, session IDs, routes and flexible payloads; strips certain fields but stores other strings. | No verified account ownership, account-wide opt-out/epoch check or full PII allowlist. Untrusted strings and paths may be identifying. A client can call it directly. |
| Server process memory | `analytics-store.ts` retains recent raw events, session-ID set, per-route/key counters and aggregate totals. | Session set and some aggregates are not bounded; cannot reliably erase one account because the events are not linked to authenticated accounts. Multiple processes/restarts must be considered. |
| Database | The repository's `0001` defines `analytics_events.user_id` nullable with `ON DELETE SET NULL`; the current ingestion `toSupabaseRow` does **not** supply `user_id`. | Deleting an auth account can orphan identifiable activity rather than delete it. Historical rows may not have a trustworthy account link; session IDs and payloads can remain identifying. The actual live schema, grants, existing data and configured sink are unverified. |
| File fallback | Unless configured off, server appends JSON lines to `data/analytics-events.jsonl` or a configured path; fallback may happen after database failure. The runbook also describes rotated files. | Append-only files/rotations do not support reliable per-account erasure; paths, access controls, deployed file stores and retention are unverified. Backups or logs may contain copies. |
| Derived copies and external systems | Local interest proposals, analytics summaries, caches, log pipelines, backups and third-party systems may be involved. | This is not a full inventory; no proof of which ones are deployed, what they contain, how long they persist or whether they permit deletion. Aggregate values may be re-identifiable. |

## Required future design

1. Inventory actual sinks and legacy writers using approved **metadata-only** inspection; do not read personal content. Establish retention, processors, backup restoration and legal holds with an authorized operator. Do not claim an inventory of real data from repository code.
2. Do not infer ownership from client-supplied IDs, matching email or old session IDs. Existing unattributed events cannot safely be assigned to a person. A reviewed strategy is required for unverifiable historical records and broad deletion; deleting everyone else's history or all legacy files would be a distinct destructive action requiring explicit approval. Do not silently relabel such records as anonymous.
3. For new account-scoped collection, use a verified Firebase identity mapped through trusted provisioning, a server-owned default-safe account preference and generation number. The server—not the request body—derives account identity. Define a minimal fixed schema with approved event types and non-sensitive, validated fields; avoid raw URLs, arbitrary free text, identifiers and high-cardinality labels. Stop or replace legacy unauthenticated ingestion only with an explicit compatibility and product-impact review.
4. Serialize opt-out and deletion with every cooperating writer; lock the preference/account and increment a server-owned generation. Reject delayed requests and writes from old generations, including retry queues and other devices; ensure no fallback to an ungoverned file/memory sink. Re-enable must not resurrect old events. Treat cross-service/network failure as incomplete, not successful erasure. An account-deletion transaction and cross-system work require a durable idempotent workflow, revocation, retries and clear status without retaining unnecessary personal details.
5. Enumerate and delete identifiable event rows, derived interests, scoped caches and approved secondary copies; remove or recalculate linkable summaries. Backups and legal holds need explicit documented retention, access and restore-time erasure replay. Only retain aggregates after a re-identification risk review; sums by small groups, rare routes, timestamps and stable IDs are not automatically anonymous.
6. Test with two synthetic accounts across multiple devices and server instances, with in-flight, pre-opt-out, stale, duplicate, out-of-order and concurrent writes, partial outages, rollback, recovery and account deletion. Verify user A cannot affect B, and no unauthorized role may erase another user. Run tests only in an approved isolated environment; staging success does not establish a production guarantee.

Until these steps are implemented and validated, the existing local controls and feed-interest proposals **must not** be described as complete server-wide opt-out or historical data erasure.
