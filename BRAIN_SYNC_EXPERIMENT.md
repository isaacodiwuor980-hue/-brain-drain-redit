# Brain synchronization — local experiment, not active

The desired behavior is account-owned brains stored in Supabase and synchronized to phones. The current app still saves brain edits locally, and the identity map is empty; the code in this document does not change that.

`supabase/proposals/0027_brain_sync_document_experiment.sql` models a new, separate snapshot store with a per-owner document revision and operation receipt. It serializes operations per operation and per document, rejects stale expected revisions, stores a receipt transactionally with the update and returns the same revision for an exact retry. It rejects reuse of an operation ID with a different snapshot or expected version. `lib/brain-sync-state.ts` separately models account-bound pending actions, uncertain results, conflicts, and acknowledgement of an old generation without marking newer edits synced. Both are unwired experiments; no live migration, transfer, or device write was performed.

The design is not ready to deploy: it duplicates `brains` rather than integrating current data, cannot establish ownership, allows a service-role caller to spoof its owner argument, does not guard owner, inherited, column, or other privileged table writers from bypassing CAS, does not validate all brain/node fields or attachment provenance, offers no public read model, tombstones, account deletion or operation retention policy, and stores complete historical snapshots in the operation journal. It requires bounded storage/privacy design, mapping provisioning, verified caller binding, atomic device persistence, multi-tab and actual concurrent DB tests, safe pull/conflict UI, offline/reconnect and deletion semantics, old-client cutover, and public/private library compatibility. Retrying an operation requires retaining its exact payload and UUID under its original verified owner. A stale acknowledgement cannot mark later local edits as synced. Never copy an unverified-owner local record into another account.

PGlite tests prove limited behavior only in a synthetic isolated fixture; sequential tests are not real concurrent Postgres tests or cross-device proof. The current branch does not call this experiment.

## Additional local components

`lib/brain-sync-local-experiment.ts` contains a separate account-keyed IndexedDB experiment. It stores the current edit and an immutable pending payload together; a late acknowledgement advances the server revision but leaves later local edits dirty, and conflict/uncertain payloads are retained. Its owner parameter must be bound to a verified active session by a future integration, and its separate database is **not included in the existing local export**. Do not use it for user data until recovery, export, deletion, quota, real multi-tab, upgrade and session-switch behavior are implemented and validated.

`api-server/src/routes/brain-sync-experiment.ts` is **not mounted** in the application router. If it were mounted it would additionally require the absent/off server flag and verified mapping; it cannot safely be enabled merely by creating the flag. It sends the mapped UUID, rejects caller-selected owners, avoids response caching, validates operation/revision shape and maps conflict/uncertain outcomes. It does not fully validate snapshot structure or attachments. HTTP tests and a mocked-auth PGlite experiment simulate two clients, a lost response retry, a stale edit and distinct accounts. They do not emulate Firebase, PostgREST, live service credentials, actual concurrent devices or the existing data model. The existing phone UI remains local-only for brain writes.

## Connected local rehearsal (not the app)

`lib/brain-sync-orchestrator-experiment.ts` joins the local journal to an injected authenticated transport for one explicit attempt; it checks the account before/after sending, retains unknown results, preserves newer edits and keeps conflicts for review. A synthetic integration test connects fake IndexedDB, the unmounted Express route and PGlite, simulates a server commit followed by a lost response, and verifies an exact retry does not make a second revision. None of these components are connected to the actual UI or Supabase. The account check alone cannot detect every same-UID sign-out/re-sign-in race, cancel in-flight writes, verify Firebase revocation, or establish server-side authorization; session-generation binding and real-device tests remain necessary. There is no auto replay or conflict resolution UI.

The local SQL experiment now revokes direct table access from `service_role` and uses a restricted SECURITY DEFINER RPC with fixed search_path. A synthetic test confirms the role can call the RPC but cannot directly insert or select the journal under fixture privileges. This is defense in depth, not complete authorization: it still accepts a caller-supplied owner UUID, and owners, superusers, inherited grants or other privileged functions can bypass or misuse it. No live change was made.


## Same-account session generation (local experiment)

The unwired coordinator now requires a provider-supplied, non-negative safe-integer session generation along with UID and token. It rejects a missing/invalid generation, does not send if the generation changes before sending, and retains the pending operation if it changes while the transport is in flight. A token refresh within the same session can retain the generation. Synthetic tests cover same-UID sign-out/re-sign-in, token refresh, malformed results and the prior lost-response replay fixture. This only works if a future real provider supplies a correctly bound generation that changes for every session replacement; no provider is wired here. A session can still change between the last check and the IndexedDB acknowledgement, a request already sent cannot be cancelled or proven uncommitted, and server identity/revocation, app integration and real-device tests are still missing. Do not use for real user data or enable cloud sync based on this experiment.

### Legacy API containment
The mounted `POST /api/brains` previously invoked `save_brain_atomic` if present. That RPC replaces the submitted node snapshot, does not check a revision, and does not round-trip all rich fields; atomicity and verified identity alone do not prevent stale overwrites or omitted data loss. The branch now returns `503`/`no-store` for every request without consulting the database, regardless of authentication or client flags. Older clients cannot save through this endpoint and must preserve unsent work rather than treating failure as success. The original SQL and PGlite tests remain for analysis, not as an endorsement of production use. The change does not revoke direct database/RPC privileges, affect other service-role writers, or change an already deployed API. No live migration was performed. The experimental CAS/journal design remains unmounted, not a replacement ready for real sync; enablement requires verified account ownership, complete field and attachment handling, durable conflict/recovery semantics and real multi-device tests.

Three legacy API success/error-path tests were replaced by fail-closed endpoint coverage; the lower-level SQL behavior tests remain.
