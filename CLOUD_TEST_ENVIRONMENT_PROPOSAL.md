**Not approved for creation or deletion.** The owner confirmed there is currently no separate Supabase or Firebase test project. The existing connected Supabase project is not a disposable test target. This plan does not authorize touching its data, creating a database branch or project, changing Firebase configuration, migrations, deployment, tests, cleanup or costs.

## Proposed setup for separate review

1. An authorized owner checks current provider pricing, quotas, regional availability, and any billing impact. Cost and availability are **unverified**; do not assume a free tier, different organization, or separate project has no charge. Choose names, region, account/organization, billing cap and access list before a separate creation approval. No credentials, service keys or tokens in chat, Git or test output.
2. Create a genuinely separate Supabase project and a separate Firebase test project through supported provider interfaces, using only synthetic configuration and no copied production accounts, content, secrets, backups, triggers, external services or production integrations. Record project references securely and identify them explicitly; repository names or localhost settings alone are not proof of isolation. Firebase is not currently available through the connected-app tools used here; owner/provider-console work may be necessary.
3. Verify both project identities in provider consoles, their resource boundaries, Firebase/Supabase URLs and credentials configuration, service-role scope, scheduled jobs, webhooks, email, storage and analytics sinks. Confirm test traffic, browser builds and worker settings cannot reach the existing project. Use a dedicated operator and synthetic accounts, never email-matching to infer ownership. Stop for any uncertainty or unexpected resource linkage. A separate project is necessary, not automatic proof of isolation.
4. Before any SQL or tests, review a schema-only compatibility comparison, the exact ordered SQL and inverse/forward-recovery plans; existing migration history differs and must not be blindly replayed. Approve test-only flags, two disposable accounts, synthetic data, traffic limits, logs, duration, retention and cleanup separately. Verify real RLS with distinct restricted roles as well as the service-mediated API. Test identity provisioning, privacy and erasure, idempotency/deletion races and failure/recovery; no real content or identities.
5. Record aggregate results and known limits. A staging pass does not prove production behavior or authorize production changes. Prepare the exact production migration, affected systems, backup, recovery, staged rollout, monitoring and rollback for separate approval. Keep new behavior off until release gates are met.

## Cleanup and cost control

Before creation, agree who owns the resources and their maximum lifetime and cost. At completion, inventory all synthetic accounts, objects and services, stop workers, revoke test access and verify no production linkage. Show the exact cleanup and project deletion steps for separate approval; deletion is irreversible and can destroy test evidence. Delete only the specifically identified disposable resources after that approval, and verify provider billing and cleanup. Never delete or reset the existing project. If any unexpected real data or integration appears, stop and report instead of cleaning blindly.
