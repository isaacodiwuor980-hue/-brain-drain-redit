# Brain Drain feed: design and release boundaries

**Status: design plus isolated local prototypes, not a completed or production-ready feed.** Existing feed and reactions are unchanged. No database migration has been applied. Assumptions below are proposals, not evidence that current services provide these inputs.

## What a person should experience

- Following: all eligible posts by followed people are reachable through pagination, subject to privacy, blocks, deleted posts and moderation. For You: a varied first visit, gradually personalized with continued exploration.
- Interest is private and separate from expertise. Opting out stops collection and use of personalized interests on the backend as well as the client; clearing removes saved interests and derived copies under an approved retention/deletion design. While off, a varied non-personal feed remains. The request that long-time users always have tags applies only while personalization is enabled and sufficient reliable observations exist; fabricating tags for opted-out or inactive users would violate privacy and accuracy.
- A downvote is not disinterest. Hide/show-less are explicit negative preferences. A lack of response is weaker evidence only after a qualified impression; it can reflect accessibility, distraction or low relevance, so never equate it with expertise or impose punishment.
- Expert-topic labels are not badges. Only an authorized human review of supporting evidence can publish a tag; candidate generation alone must not do so.

## Replaceable stages and signals

1. Inputs: authorized server-side post data and preferences; qualified impression, visible duration, opening, positive reaction, comment, share, follow, hide/show-less and skip. Event IDs must be generated with stable retry semantics, deduplicated per account/session, rate-limited, verified against the displayed post, and never logged with raw content or full identifiers. A qualified impression needs foreground visibility and a configurable minimum visible area/time; exact thresholds, sampling, accessibility and bot resistance need validation. A downvote by itself is excluded from interest evidence. A recorded impression is not proof the user read or understood the post.
2. Candidates: obtain permitted followed/circle and other eligible posts using stable cursors and authorization checks; no public candidate is guaranteed to be safe merely because it has a high score. The current feed fetches pages chronologically; no server-level personalized candidate generator is implemented.
3. Scoring: interest, quality, recency, reviewed authority and symmetric bridge can be separate signals; no view-based expertise. Tier weights and expert effects are policy parameters requiring calibration and fairness review, not factual accuracy. 0.10 Mouth is allowed in the additive prototype; legacy code differs and is untouched. Tier inputs must be genuine user choices from verified identity and trusted server data, never inferred from legacy defaults.
4. Ranking/diversification: seeded stable tie-breaking, exploration slots, and reviewed caps across authors/topics/sources. Pure local prototypes `buildOfflineFeed` and `diversifyOffline` are unwired: the latter uses best-effort rolling caps and preserves all candidates even when caps cannot be satisfied. It does not reserve exploration slots. Its worst-case cost is quadratic and must be benchmarked and improved for real feed sizes.
5. Final ordering: preserve the ranked order through presentation. The current HomeFeed re-sorts after the experimental order, so this requirement is not met. Do not wire the incomplete experiment to a soft client-only switch.

## Candidate formulas (proposals only)

- Topic interest can use decaying engagement: for observation age `d`, weight `w = 0.5^(d / halfLife)`, then `(prior/2 + sum(w for positive engagement)) / (prior + sum(w for qualified exposures))`. This is a heuristic, not a probability that a person likes a topic. `prior` and `halfLife` are explicit configuration inputs; no production values have been selected. Explicit hide/show-less requires its own override; it is not implemented in the prototype. Guard duplicates, stale/future timestamps, repeated exposures, and sample sufficiency.
- Expert candidates require multiple independent, trusted sources of evidence and sustained quality over time. A future calibrated score could combine evidence volume, consistency and independently sourced quality with uncertainty and a configurable threshold. Until evaluation demonstrates calibration, do not call it a probability, create an automatic public label or use interest/views as evidence. Human review and appeal need a separate authorized workflow.
- A potential post score can blend normalized relevance, quality, freshness, reviewed authority and a symmetric bridge factor using explicit, reviewed weights. No numeric weights are authorized as production defaults, and the local generic scorer does not implement this formula. Reaction consensus is not proof of factual truth.
- A future ML scorer may provide a normalized score alongside a deterministic rules scorer; use `combined = (1 - blend) * rules + blend * model`, with blend default zero. Validate model inputs and outputs; if unavailable, slow, invalid or failing, fall back to rules. The local prototype tests exception/invalid-score fallback, not timeouts, monitoring, model fairness or operational deployment.

## Points and reaction safety

Design-only: non-cash, non-transferable starting grant of 1000; all grant/reserve/release/burn movements recorded in an append-only ledger. A single database transaction should authenticate and map the account, validate trusted topic/tier eligibility, serialize the balance and current vote, deduplicate operation IDs, reserve no more than the balance, update vote and counts, and append balanced ledger events. Duplicate requests with the same idempotency key but different payload must be rejected. Stale or out-of-order actions need a reviewed versioning protocol. Loss burns points, never transfers them; outcomes, finality, dispute and appeal handling are not defined. No automatic penalty or actual ledger is implemented. Existing legacy toggle is multiple REST operations and has not been proven safe under concurrency.

## Switch, shadow and safety

The current status check is a cooperating-online-client soft switch, not an instant server kill switch. A future server-side fail-closed flag must be checked at the point of ranking, with fast invalidation and a tested latency target; serve the unchanged legacy feed on disabled/unavailable/timeout/error. Older and offline clients require a separate compatibility plan: no absolute universal instant guarantee. Shadow mode must be off by default, read-only, with privacy-safe aggregate metrics and no second write or point movement; compare equivalent snapshots with useful coverage. Existing system does not meet these requirements.

## Database and rollout

Live schema and recorded migrations remain unknown because read-only Management API inspection returned 28P01. Do not modify previously applied migrations or infer schema from repository files. Proposed future tables for private interest settings/signals, expert-review evidence and point ledger need reviewed foreign keys, indexes, RLS, service-role authorization, concurrency tests and non-destructive forward migrations. Every rollback that loses data needs explicit approval and a verified backup. Write and test migrations locally only; no Supabase application without separate authorization.

Gate rollout on schema and identity reconciliation, independent PostgreSQL concurrency, privacy and isolation tests, meaningful shadow comparison, app/browser/device testing, performance budget, abuse/fairness review, monitoring and tested rollback. Also confirm historical token revocation, review Firebase browser-key restrictions, and reconcile migration history before launch.
