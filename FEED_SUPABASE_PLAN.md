# Feed database reconciliation plan — review only

**Status: NOT approved for database changes.** No SQL in this plan or repository is authorized for execution on the connected project. The only completed live activity was read-only metadata inspection. Production readiness cannot be established by a deadline alone.

## Verified facts and constraints

- The connected project reported healthy services on the last check. `LIVE_SCHEMA_SNAPSHOT.md` records the exact limited metadata; it does not prove user data is intact or backed up.
- Its recorded migration names differ from repository `0001`–`0011`; manual history is unknown. Never edit or blindly replay possibly applied migrations. A green local fresh-database test does not establish compatibility with an existing database.
- Existing `follows` uses UUID follower and following IDs. The branch asks for a different table; other feed paths use Firebase subjects where observed database columns require UUIDs. `posts.tags`, `user_identity_map`, selected flags, tier tables and selected RPCs are not present in the inspected public schema. The draft PR can therefore break functionality if merged and deployed as-is.
- Identity cannot be established from an email address, interest tag, or client-supplied UUID. `IDENTITY_ENFORCEMENT=off|shadow|enforce` with default shadow and mapped UUIDs for UUID columns remains a design requirement, not implemented. UUID columns must fail closed for unmapped users; text fallback must only apply to known text columns. Deployment order and safe mapping/provisioning for existing accounts are unverified.

## Ordered work and controls

1. **Protect existing data.** Identify deployments and automatic integrations; confirm a restorable backup with its owner without exporting user content here. Record current schema, policy/grant/function/trigger definitions and migration history privately and safely, review data classifications, and plan restoration. Risk: backups may be incomplete or restoration may incur downtime; verify by restoring to an isolated environment, not overwriting real data. Undo: stop before changes.
2. **Reconcile identities and schema.** Compare actual definitions with branch requirements; design forward-only changes and one-to-one verified Firebase-to-Supabase identity provisioning/recovery. Run a read-only, no-personal-data mapping coverage assessment after the design is approved. Risk: incorrect mapping can expose another user's data, while missing mappings can lock users out. Verify with two-user isolation, unmapped/error behavior, migration compatibility and rollback on independent staging; never match by email. Undo: revert consuming code first; do not delete mappings or user data without separate approval and a tested backup.
3. **Compatibility before feed rollout.** The Following route should use the verified follow schema only after mapped identity and pagination are designed and tested. Keep legacy response behavior when the new algorithm is off. Address the `posts.tags` mismatch only through an independently reviewed forward migration and matching application deploy order. Risk: missing columns or incompatible queries can blank the feed. Verify against a representative isolated database with existing data and compare legacy behavior. Undo: disable the new code and restore previous application version; preserve stored data.
4. **Local tier boundary prototype.** `supabase/proposals/0012_tier_eligibility_v2.sql` adds a separate, service-only setter: authority 0.10 can select Mouth, then Lunch at 0.35, House at 0.55, Life at 0.75. The earlier 0011 setter remains unchanged and allows Life at baseline. The new path locks the same per-user/post key and existing grant before checking, then calls the old setter. Test `lib/tsrg/tier-eligibility-v2.integration.test.ts` on PGlite verifies boundaries, removal after revocation, privilege checks, rollback and reapply locally. The initial red test was a missing migration file, not a red/green test of a deployed fix.
   - **Critical limitations:** no account-age enforcement, idempotency key, cross-client action ordering, point reservation/ledger/burn, real multi-session concurrency, prevention of writes through the old function, live RLS verification or real client/API integration. Existing REST writers do not share this lock. Never route live users to this function as a finished solution.
   - `supabase/rollbacks/0012_tier_eligibility_v2.sql` removes the V2 function only after all consumers are stopped. It preserves vote rows but does not undo prior votes. Returning to the legacy setter changes enforcement and requires explicit policy approval. No rollback on real data without authorization and verified backup.
5. **New feed and controls.** Build trusted signal inputs, private opt-out/clear enforcement, candidate generation, deterministic ranking, reviewed expert-tag queue, safe points ledger and idempotent reaction mutation as separate modules. Serve legacy feed on flag off/error; a cooperating-client poll is not an instant universal kill switch. Test opt-out against storage and use, cross-user access, stale requests, crashes, 50 independent concurrent clients on isolated PostgreSQL, and meaningful abuse/fairness scenarios. Risk: wrong scores, privacy leaks, point losses and incorrect ordering. Undo: server-side disable, stop writes, revert application, preserve ledger; never delete data without approval.
6. **Release gates.** No merge or deployment until migration reconciliation and identity compatibility are resolved, verified backup/restore and staged rollback exist, local and independent database/browser tests pass, policy/calibration and accessibility reviews are complete, privacy-safe metrics and shadow comparison meet agreed thresholds, and token/key issues are resolved. Merging `main` may trigger staging deployment depending on configuration; external integrations unknown.

## Safe checks and proposed SQL
