# Feed database reconciliation plan — review only

**Status: NOT approved for database changes.** No SQL in this plan or repository is authorized for execution on the connected project. The only completed live activity was read-only metadata inspection. Production readiness cannot be established by a deadline alone.

## Verified facts and constraints

- The connected project reported healthy services on the last check. `LIVE_SCHEMA_SNAPSHOT.md` records the exact limited metadata; it does not prove user data is intact or backed up.
- Its recorded migration names differ from repository `0001`–`0011`; manual history is unknown. Never edit or blindly replay possibly applied migrations. A green local fresh-database test does not establish compatibility with an existing database.
- Existing `follows` uses UUID follower and following IDs. The branch asks for a different table; other feed paths use Firebase subjects where observed database columns require UUIDs. `posts.tags`, `user_identity_map`, selected flags, tier tables and selected RPCs are not present in the inspected public schema. The draft PR can therefore break functionality if merged and deployed as-is.
- Identity cannot be established from an email address, interest tag, or client-supplied UUID. `IDENTITY_ENFORCEMENT=off|shadow|enforce` with default shadow and mapped UUIDs for UUID columns remains a design requirement, not implemented. UUID columns must fail closed for unmapped users; text fallback must only apply to known text columns. Deployment order and safe mapping/provisioning for existing accounts are unverified.

## Ordered work and controls

1. **Protect existing data.** Identify deployments and automatic integrations; confirm a restorable backup with its owner without exporting user content here. Record current schema, policy/grant/function/trigger definitions and migration history privately and safely, review data classifications, and plan restoration. Risk: backups may be incomplete or restoration may incur downtime; verify by restoring to an isolated environment, not overwriting real data. Undo: stop before changes.
2. **Reconcile identities and schema.** Compare actual definitions with branch requirements; design forward-only changes and one-to-one verified Firebase-to-Supabase identity provisioning/recovery. Run a read-only, no-personal-data mapping coverage assessment after the design is approved. Risk: incorrect mapping can expose another user's data, while missing mappings can lock users out. Verify with two-user isolation, unmapped/error behavior, migration compatibility and rollback on independent staging; never match by email. Undo: revert consuming code first; do not delete mappings or user data without separate approval and a tested backup.
3. **Compatibility before feed rollout.** The Following route should use the verified follow schema only after mapped identity and pagination are designed and tested. Keep legacy response behavior when the new algorithm is off. Address the `posts.tags` mismatch only through an independently reviewed forward migration and matching application deploy order. Risk: missing columns or incompatible queries can blank the feed. Verify against a representative isolated database with existing data and compare legacy behavior. Undo: disable the new code and restore previous application version; preserve stored data.
4. **Local tier boundary prototype.** `supabase/proposals/0012_tier_eligibility_v2.sql` adds a separate, service-only setter: authority 0.10 can select Mouth, then Lunch at 0.35, House at 0.55, Life at 0.75. The earlier 0011 setter remains unchanged and allows Life at baseline. The new path locks the same per-user/post key and existing grant before checking, then calls the old setter. Test `lib/tsrg/tier-eligibility-v2.integration.test.ts` on PGlite verifies boundaries, removal after revocation, privilege checks, rollback and reapply locally. The initial red test was a missing migration file, not a red/green test of a deployed fix.
   - **Critical limitations:** no account-age enforcement, idempotency key, cross-client action ordering, point reservation/ledger/burn, real multi-session concurrency, prevention of writes through the old function, live RLS verification or real client/API integration. Existing REST writers do not share this lock. Never route live users to this function as a finished solution.
   - `supabase/rollbacks/0012_tier_eligibility_v2.sql` removes the V2 function only after all consumers are stopped. It preserves vote rows but does not undo prior votes. Returning to the legacy setter changes enforcement and requires explicit policy approval. No rollback on real data without authorization and verified backup.
5. **New feed and controls.** Build trusted signal inputs, private opt-out/clear enforcement, candidate generation, deterministic ranking, reviewed expert-tag queue, safe points ledger and idempotent reaction mutation as separate modules. Serve legacy feed on flag off/error; a cooperating-client poll is not an instant universal kill switch. Test opt-out against storage and use, cross-user access, stale requests, crashes, 50 independent concurrent clients on isolated PostgreSQL, and meaningful abuse/fairness scenarios. Risk: wrong scores, privacy leaks, point losses and incorrect ordering. Undo: server-side disable, stop writes, revert application, preserve ledger; never delete data without approval.
6. **Release gates.** No merge or deployment until migration reconciliation and identity compatibility are resolved, verified backup/restore and staged rollback exist, local and independent database/browser tests pass, policy/calibration and accessibility reviews are complete, privacy-safe metrics and shadow comparison meet agreed thresholds, and token/key issues are resolved. Merging `main` may trigger staging deployment depending on configuration; external integrations unknown.

## Local-only preference proposal (not a completed privacy feature)

`supabase/proposals/0013_feed_privacy.sql` proposes separate per-user preferences and topic-interest rows with RLS and service-only functions. Default is off as a conservative prototype assumption. A preference-row lock is shared by the cooperating SQL functions; `feed_set_personalization(..., false)` removes that account's rows, `feed_clear_interests` clears while leaving the setting unchanged, and reads/writes respect off. Tests use PGlite with fake accounts, not the real Supabase instance.

This **does not implement settings UI, event collection, scorer integration, end-to-end opt-out/clear, or verified live identity provisioning**. A limited authenticated API was subsequently added, as described below; it does not provide complete privacy controls. It does not remove existing analytics, local caches, other derived data or backup copies. The proposal now includes a per-account epoch: cooperating writers must supply the epoch captured at event collection, and clear or disable invalidates earlier epochs. This guard is not wired to an event producer or consumer; obtaining the epoch when processing an old event defeats it. The whole capture/queue/processing lifecycle still needs design and enforcement. Direct service-role table access and existing writers bypass these functions; read results already in flight may outlive an opt-out. A real multi-session test, privacy/retention review, an approved ownership/privilege design, and all-writer inventory are release gates. The separate rollback file contains instructions only, not executable destructive SQL; a reviewed data-preserving rollback and backup are required before deployment. The SQL is outside the automatic migrations directory and must not be applied to Supabase without a reviewed plan and explicit approval.

## Following v2 local endpoint — not enabled or integrated

`GET /api/feed/following-v2` is a separate, default-unavailable server-gated endpoint. It requires a verified Firebase token and mapped Supabase UUID, queries `follows.follower_id` / `following_id`, validates each returned UUID, excludes the absent `posts.tags` column, and does not use the shared feed cache. It does not alter the legacy `/api/feed` endpoint and is not called by the browser. When the server flag is absent/false the endpoint is unavailable; a missing or failing flag table returns 503. No flag is provisioned or enabled on live Supabase.

**Release blockers:** The live identity mapping and feature flag tables do not exist and verified mapping coverage is unknown. The existing follow-write path still targets `user_follows` and must be reconciled. Real PostgREST relation embedding (especially profiles), visibility rules with the service role, RLS/access controls, mapped reaction display across the client identity boundary, pagination stability under inserts and account isolation must be tested on isolated staging. The endpoint limits follow graphs to 500, and relies on PostgREST returning at least 501 rows to detect larger graphs; a lower server row cap could silently truncate results. Replace this with an indexed, server-side paginated join before rollout and test large graphs. Reaction aggregation may also hit PostgREST row limits. Rate limiting and the front-end switching/fallback behavior remain unimplemented. This code is not a production-ready feed and must not be enabled merely because local mock tests pass.

## Limited privacy API (local code; not live or UI-integrated)

`GET`, `PUT` and `DELETE /api/feed-privacy` use verified auth and the mapped caller UUID, no-store headers, and the existing IP-based auth-tier limiter. GET reads only the proposed preference table; PUT sets the proposed feed-interest preference; DELETE clears the proposed interest rows without disabling the preference. Responses explicitly identify the narrow `proposed-feed-interests-only` scope. Turning on requires the default-unavailable server flag `feed_interest_tracking_v2`; turning off and clearing deliberately remain callable with that flag off or unavailable so a kill switch cannot prevent a user's privacy request. They still fail with 503 if identity or storage is unavailable. No production setting exists until the separate schema, identity mapping and flag are reviewed and provisioned.

This is **not a site-wide privacy switch**: it does not stop or delete existing analytics, queues, local storage, caches or backups, and there is no UI or connected tracking path. GET/clear/disable are new endpoints not gated by the enable switch, but need authenticated identity and the proposed tables; no existing user behavior changes. The proposed SQL now takes a shared lock on the server flag row inside enable, interest read and interest write transactions, so cooperating flag updates serialize with these operations; this remains unverified under independent PostgreSQL sessions. Requests already in flight may finish before the flag update commits, and results already returned cannot be recalled. Other collection/read/serving paths must also honor the switch before rollout. A switch off/on cycle does not invalidate queued event epochs, so old queued events require additional invalidation design. IP rate limits fall back to per-instance memory if Redis is unavailable and do not constitute verified distributed per-account abuse protection. Real Firebase verification, PostgREST/RLS/role privileges, SQL rollback, simultaneous transactions, retention and effective deletion need staging review. Do not enable or present this as complete opt-out/clearing functionality.

## Browser activity control in Settings

A separate browser-only control now enforces the existing `lib/analytics.ts` activity path: when off, its IndexedDB transaction rejects new events, reads hide saved activity from consumers, and the backend queue checks the current preference and epoch before sending. Clear removes only the `analytics_events` IndexedDB store and invalidates queued epochs; it asks for confirmation in the UI. The setting is browser-wide, not account-wide or synchronized, and old activity stays saved when switched off until explicitly cleared. Existing legacy behavior is preserved by default if no preference exists; a previously saved `dataCollection: false` is honored even though the old switch did not enforce it. Followed topics and other signals still influence ranking. Turning on restores use of previously saved activity unless it was cleared.

Transactions and error handling are exercised with fake IndexedDB and happy-dom; they do not prove behavior in real browsers or across separate processes/tabs. In-flight requests can already have reached the server before cancellation, and other services, direct requests, local/cloud data, caches, logs and backups are not covered. LocalStorage notifications for other tabs are best-effort; real multi-tab lifecycle and cache race tests remain a release gate. The server privacy proposal is separate and not integrated with this UI. Do not describe this control as a complete account-wide privacy or deletion solution. The `sendBeacon` path now falls back to checked asynchronous delivery and may lose events at page close.

The browser event queue additionally drops pending events if it cannot read the activity preference, and treats a browser storage-clear notification as a privacy change. The local-data clear UI signals its own tab before and after IndexedDB clearing. Simulated in-flight abort and storage-clear tests pass; these cannot prove delivery cancellation or real multi-tab behavior, and a browser-storage reset can reset the local preference/version. Actual browser lifecycle, concurrent tab and account-wide deletion tests remain required.
