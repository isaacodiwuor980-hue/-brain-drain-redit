# Follow identity migration rehearsal — no live SQL approved

## Evidence and problem

The owner authorized metadata inspection and selected: retain records with unverified ownership; review exact live changes before each stage; skip deployment. The selected live metadata in `LIVE_SCHEMA_SNAPSHOT.md` shows `follows` (UUID foreign keys to `auth.users`) and `user_follows` (text identifiers, no foreign keys in the selected constraint result). They have different policy semantics. The legacy application writes Firebase subjects to the text table and mixes in UUID-shaped target IDs; following-v2 reads mapped UUIDs from `follows`. No trusted relation between the two identifier spaces is established. A UUID-looking string or matching email is not proof of ownership. The observed policy allowing either endpoint of a text relationship in an ALL policy needs review against intended permissions; service-role operations bypass RLS.

The current branch's mounted `/discover/follow` is now hard-disabled before writes, but that is **local code only**: it does not change an already deployed service, revoke direct database access, disable privileged functions or stop older clients. The old writer remains an unmounted audit fixture, not a safe migration path. Both tables and existing rows remain untouched.

## Rehearsal sequence

1. Complete a metadata-only inventory of all follow readers, writers, triggers, constraints, policies, grants and identity providers. Reconcile historical schema drift with an authorized operator. Determine intended semantics for who can create/delete a relationship and who can read follower/followee lists; account for blocks, private profiles, deletion, notifications and counters. Do not inspect personal content or assume tables are empty.
2. Define authoritative, server-verified identity provisioning without email inference: map a Firebase subject to a Supabase identity only through a reviewed, authenticated binding workflow. Enumerate unmatched/ambiguous/conflicting identifiers as held records without altering their source. Browser-local data must be handled on its owning device with a verified account and explicit review; agent access to the repository is not access to all devices or Firebase data.
3. Model representative schemas and *synthetic* identities in a local PostgreSQL-compatible fixture. Test migration preconditions, uniqueness, self-follow, nonexistent principals, two-account authorization, followee attempting an unauthorized write, direct role access and privileged/service-role bypass. Verify new follow/read/unfollow workflows, idempotency, concurrent writes, race with account deletion, partial failures, reversible or forward-repair behavior and legacy-client incompatibility. Never use real rows for tests.
4. Prepare exact versioned forward SQL and application change only after schema/identity/visibility decisions are established. Include the precise before/after policies and grants, lock/downtime analysis, real-data scope, no-delete/no-overwrite invariants, preconditions and postconditions, monitoring, rollback limitations, authorization impacts and handling of unknown records. A policy-only fix does not stop privileged bypasses; a client-only pause does not secure database access. Do not automatically select `follows` or `user_follows` as authoritative.
5. Seek the owner's review of **each exact live stage** before execution. Stop on drift, unexpected objects, identity ambiguity or partial failure; do not guess SQL, coerce IDs, retry uncertain writes, replay under a different account, or delete held records. The user said not to worry about backups, but no restore has been verified; document the resulting data-loss and recovery risks rather than claiming they are solved. No SQL, migration, data move, live test or deployment is authorized by this document.

## Local policy reproduction

Two tests passed. This supports the policy concern but does not establish live effective access, exhaustive grants, API exposure, or intended semantics. It does not alter or connect to Supabase.
