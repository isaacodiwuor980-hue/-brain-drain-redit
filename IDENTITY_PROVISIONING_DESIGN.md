# Identity mapping provisioning design — not implemented or run

This is a proposed operator-reviewed process, not an executable script. It does not authorize use of real data or any environment. Never map by email, display name, UUID shape, user-supplied values, or other untrusted attributes.

1. An authorized operator establishes a trusted, audited linkage between each authenticated Firebase subject and the corresponding Supabase auth.users UUID using an approved account-linking process. Ambiguous, missing or conflicting pairs are quarantined for manual resolution, never guessed. Choose the proof of linkage and account recovery policy before implementation.
2. A future restricted admin-only tool consumes the reviewed pairs via a secure local input mechanism, validating subject length/charset, UUID syntax, existence of the auth user and uniqueness in both directions. No secrets or full identifiers in logs. It must run with least privilege, explicit operator authorization, and deny browser/service-key exposure.
3. **Dry-run is the default** and performs no writes; it reports only aggregate counts: exact matches, proposed inserts, missing users, duplicate subjects, duplicate UUIDs and conflicts. It must not print PII, emails, tokens or full IDs. Require operator approval of the report and verified backup/restore before considering a write.
4. In a single transaction or safely resumable batches, insert only missing pairs. An existing identical mapping is a no-op; a conflicting subject or UUID aborts/quarantines rather than overwriting. Database unique constraints must arbitrate concurrency. Re-running the same input is idempotent. Do not automatically remove or change mappings.
5. Record who approved the operation, timestamp, change counts and a non-sensitive batch identifier in an auditable store; protect and retain this record according to approved policy. Restrict access, support incident review and verify post-write counts. Handle deletions, account recovery and mapping revocation using a separately approved workflow.
6. Test offline with synthetic records, duplicate/conflict/retry/race cases and proof of rollback. Later, after separate authorization and backup verification, test in isolated staging with disposable identities, before any production decision. No implementation or real-user import exists yet.

## Offline aggregate planning experiment

`api-server/src/lib/identity-link-plan.ts` is an unwired pure helper tested with synthetic pairs. It takes assumed-reviewed pair and user snapshots and returns aggregate category counts only; it does not fetch, print, persist or apply mappings. It quarantines duplicates and conflicts, including a valid identifier also present on a malformed input row. It cannot prove account ownership or check snapshot freshness, race conditions, role security, approval or completeness. A genuinely authorized ownership-proof and operational process are still required; do not use this experiment to create live mappings.

## Review-only restriction of API mapping writes

The local 0007 scaffolding grants the API service role direct DML on the map. In a synthetic PGlite test, that role could insert a link without proving ownership. Review-only proposal `0017_identity_map_service_grants.sql` revokes its explicit direct mutation grants while retaining SELECT; a local test verifies denial of insert, update and delete, and verifies the proposal can be applied twice. This is defense in depth, **not ownership proof**: it does not audit inherited or column privileges, owners, privileged functions or other roles, and an API service may still read mappings and call other privileged functions. Account deletion and privileged provisioning/recovery need separately reviewed workflows; the rollback restores unsafe direct write grants and has not been tested. No live SQL has been run.
