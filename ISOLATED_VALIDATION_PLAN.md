## Environment and operator prerequisites

1. The owner chose to create and connect separate test projects. An authorized operator creates a **separate, disposable** Supabase project and a separate Firebase project, with no copied production data, backups, users, secrets, or integrations that can affect production. Verify names and immutable project references in the provider consoles, billing/region, owners and project isolation. Identify the disposable project to the assistant through the connected app, not by sharing secrets. Confirm it is not the live project immediately before every write or cleanup.
2. Separately approve the exact test environment, synthetic test data, SQL files, API deployment (if any), test accounts, test duration, approved test load and cleanup. Approval of this plan alone is not approval to run it. Do not enable experimental ranking, staking, point losses or a production flag. If an experiment needs a test-only flag, scope and approve it explicitly and keep it out of production.
3. Establish restricted operator and test-user access; use provider-supported authentication and a proper supported SQL interface. Keep privileged credentials in the environment's managed secret store, never in chat, source control, browser bundles, terminal transcripts or test outputs. The service-role key is not an ordinary user's RLS identity; never use it to claim two-user isolation.
4. Capture a sanitized schema-only snapshot, migration history, relevant grants, ownership, inherited/column permissions, policies, functions and triggers. The isolated target must be reconciled to a reviewed production schema representation **without copying personal rows**. Existing local migrations differ from the observed live history; no file should be blindly applied. Establish an ordered forward plan and rollback per object, independently review destructive steps and dependent writers, and verify a backup/restore drill for any environment where data matters.
5. Use at least two newly created disposable test accounts and one unauthenticated client. To test identity ownership and account deletion, test both the Firebase boundary and the actual database role/account, not merely mocked HTTP or service-role requests. The new-account provisioning protocol must be implemented and security-reviewed first; it currently is not. Existing users remain unlinked pending an approved recovery design.

## Test sequence and stopping conditions

- **Baseline:** record application commit, test project identity in the secure operator record, schema versions, configuration, test date and commands without recording tokens or personal content. Verify no production connection in the app, SQL client, background jobs, analytics sinks or browser. Confirm all experimental controls are off and retention/cleanup is scoped to the disposable project.
- **Migration rehearsal:** in an empty disposable database, apply only the reviewed ordered changes and verify object definitions and expected grants. Repeat/retry where the migration promises idempotence; independently check downgrade/forward recovery on disposable data, including what is and is not restored. Rehearse a second schema-representative synthetic database only after reconciling differences. Any unexpected privilege, schema mismatch, partial application or data loss stops the run.
- **Identity:** exercise new-account creation from freshly verified Firebase authentication through trusted server-side creation/linking, with two separate synthetic users; forged client UUIDs, unauthenticated requests, conflicts, retries, concurrent creation and failed/partial provider operations must not create or change a link to another account. Test session freshness, revocation/recovery and cleanup to the extent supported by the approved design. Inspect the result through authorized test-only channels. Existing-account mapping must stay unavailable.
- **Authorization:** with actual distinct restricted account roles/tokens (not service-role substitution), test unauthenticated, own-account and cross-account read/write/delete, including public/private brains, posts, reactions, settings and mapped UUID ownership. Also test API service-mediated routes, effective permissions, restricted functions and RLS. Visibility must be rechecked on recommendations; an error or unknown permission must fail closed. Treat all findings as defects; do not work around them by linking identities on email or by making resources public.
- **Privacy:** use only artificial events/identifiers. Verify account-scoped disable, deletion, late/stale writes, retries, multiple clients, reloads, derived interests and backend storage. Check every approved sink and log boundary; request completion must reflect partial failures and backups/retention must not be presented as already erased. Current old analytics lack reliable ownership provenance, so this test cannot establish historical erasure until a safe history strategy is reviewed.
- **Concurrency:** independent restricted sessions should exercise atomic reactions, follow writes, interest opt-out/clear vs ingestion, provisioning conflicts and deletion vs wallet operations using barriers. Record aggregate outcomes and final synthetic state. Include rollback, duplicate requests and error cases; no point penalties or real balances.
- **Browser and operations:** test current supported devices/browsers, sign-in/out, privacy controls, feed rendering and rollback/fail-closed behavior. Verify monitoring, rate limits, alerting, dependency outages, migration rollback and restoration in the isolated environment. Conduct authorized synthetic performance and abuse tests at a preapproved load. Capture aggregate metrics only; synthetic benchmarks do not prove real-user fairness, correctness, production RLS or future availability.

Stop immediately on any connection to the wrong environment, use of real accounts or data, unexpected permissions, dangerous errors, unintended external traffic or missing approval. Do not delete diagnostic evidence containing real data; alert the authorized operator. Clean up only specifically approved disposable objects after recording aggregate results. Never delete or reset a live project as a test.
