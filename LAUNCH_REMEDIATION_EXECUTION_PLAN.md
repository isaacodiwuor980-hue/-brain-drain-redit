## 9. Image storage design and migration (not implemented)

Supabase can be both the PostgreSQL provider and an object-storage provider: a verified design could store image bytes in Supabase Storage and keep an authorized object reference plus metadata in PostgreSQL. This repository does not establish that an image bucket, upload integration, policies or recovery have been configured. `PostCreator` currently reads selected images as browser data URLs; the post API accepts URL strings rather than uploading bytes; profile images use a separate data-URL path. Do not tell users that these already persist in Supabase Storage. The current social client holds image and note posts as device-only drafts; this is not a server access-control boundary.

Before enabling image publication, inventory every image/attachment producer, reader, legacy client and existing record, plus format/size limits and where bytes currently reside, without inspecting personal content. Design separate public and private access rules enforced by the storage service, verified subject/owner binding, unguessable object paths, content-type/size validation, safe rendering, lifecycle and deletion, quotas, upload authorization, ownership changes, and handling of orphaned objects. Avoid storing secrets or permanent private access tokens in URLs. A public image must be intentionally public; private objects must not become accessible through public buckets or caches. Evaluate provider plan/limits without adding a paid service.

Design staged, account-bound and idempotent upload/commit with durable local preservation and explicit uncertain-result handling: uploading bytes and inserting a DB row are not a single transaction. On failure do not blindly retry or delete possibly referenced objects; provide a reviewed reconciliation process. Verify revocation, stale links and CDN caching, cross-account access, concurrent replacement, privacy changes, malicious files and outage behavior using synthetic objects in an approved isolated environment. Storage object contents are not automatically covered by database backups; demonstrate separately approved recovery and deletion-state reconciliation. Only after schema/history reconciliation, recovery evidence, reviewed exact policies, tests and specific live approval may any bucket, migration, live data transfer or flag change occur. Existing data URLs and local-only drafts must be inventoried and migrated only with verified ownership and an explicit non-destructive migration/reconciliation plan.
