# Proposed production validation with synthetic accounts — NOT APPROVED TO RUN

The owner requested a proposal for narrowly scoped synthetic production tests. This is not authorization for production test accounts, writes, migrations, test traffic, deployment, feature changes, real-user access, cleanup, or execution. The current production project must not be assumed to be a test environment. First complete and review the separate disposable Firebase/Supabase staging plan in `ISOLATED_VALIDATION_PLAN.md`. Passing staging reduces risk but does not make production testing safe or prove real-user behavior.

## Required concrete approval package

Before requesting permission for a production test, an authorized operator and reviewer must provide and confirm, in secure systems rather than chat:

- Exact project/environment identity, ownership, version/commit, deployment topology, support contact, approved window, and incident stop/rollback owner. Independently re-confirm the target and that no data from a real user will be viewed or altered. Never paste keys, tokens or personal identifiers into chat or logs.
- Evidence that relevant production schema, migration history, grants, RLS, functions and triggers have been reconciled by read-only metadata inspection; identify a supported database interface and least-privilege test roles. No schema changes or service-role writes are implied by this proposal. Actual current schema differences and missing identity tables/functions are documented in `LIVE_SCHEMA_SNAPSHOT.md`.
- A verified backup/restore process and review of rollback/cleanup and any third-party, trigger, notification, webhook, billing, email, feed, monitoring, retention, rate-limit or scheduled-job side effects. A backup is not permission to delete or overwrite data. Abort if a test could reach a real person or affect their content.
- A reviewed written allowlist containing exact operations/endpoints and database objects, bounded volume/rate/duration, exact synthetic account creation method, identity provisioning and credentials handled outside chat, test-only marker, expected outcomes, prohibited operations, how synthetic rows are located, and how each created object will be removed. Cleanup must be limited to confirmed synthetic objects, independently verified, and explicitly approved. If safe isolation/cleanup cannot be demonstrated, do not run production writes.
- Acceptance criteria, privacy-safe evidence and audit plan, and explicit per-operation authorization covering any creation, update, deletion, test workload and cleanup. Obtain separate permission for every production migration, deployment, flag change or data deletion. Never infer approval from approval of this proposal.

## Candidate narrowly scoped tests (not yet runnable)

1. **Read-only checks:** validate health, schema definitions and security configuration without accessing personal content or raw credentials. Public routes must not disclose synthetic private IDs. Record sanitized outcomes and identify any production incompatibilities; do not assume a metadata check verifies RLS.
2. **Controlled identities:** only if the new-account-only provisioning flow is implemented, independently reviewed and deployed with separate approval, create two explicitly approved synthetic accounts through a trusted flow. An absent mapping is not proof of new-account eligibility. Do not map pre-existing real accounts, import identifiers, use email matching, or bypass provider verification. Verify cleanup covers both identity providers without deleting anyone else's account.
3. **Authorization:** using the actual two restricted test identities and unauthenticated access, attempt own-account and cross-account reads/writes against only allowlisted synthetic resources. Include private/public visibility and no-store error paths. Service-role calls do not prove user RLS. If no safe test objects or separate roles exist, stop; never use actual users' private data as test fixtures.
4. **Privacy lifecycle:** only once a complete, reviewed account-scoped ingestion/erasure workflow exists and is separately approved, create clearly marked synthetic events; disable tracking and verify old events and derived data are removed and late/stale writes fail across writers. Test retry and partial failure only within agreed boundaries. Current legacy ingestion cannot reliably attribute historical events to accounts, so it cannot pass this criterion yet. Avoid including sensitive strings in logs.
5. **Concurrency:** concurrency and load testing must first run in staging. Any production concurrency must be separately authorized with a conservative budget and demonstrably isolated synthetic rows, with side effects and capacity monitored. No tier stakes, automatic penalties or experimental feed rollout.
6. **Cleanup:** only with explicit approval and exact synthetic scope, delete just the test-created objects and accounts; verify remaining synthetic artifacts and report failures. Backup and log retention means immediate total erasure cannot be assumed.

Stop on wrong project, unexpected account/resource ownership, real-user exposure, schema mismatch, unknown trigger behavior, unintended notifications or downstream writes, abnormal latency, access failure, or any safety uncertainty. Report aggregate findings and stop; do not repair the production system during testing without a new, specific approval.

## Evidence and limitations

Record only what was actually tested, time, commit/schema versions, restricted-role outcomes, aggregate pass/fail and known omissions. A small canary does not establish complete production RLS, fairness, privacy, performance, account ownership, or correctness for every user. A launch still requires all other release gates and a separate deployment decision.
